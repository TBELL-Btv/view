1. 배경

  • 고객사(SK브로드밴드)로부터 셋톱박스 화면·기능에 대한 테스트 자동화 요청을 접수했다.
  • 당사는 자체 기준으로 1차 설계를 완료했고, 실기기 실측을 통해 기술 제약을 사전 검증했다(부속서 2장). 이 실측 결과는 견적·설계의 전제로 제공되며, "해보니 안 되더라"를 계약 후에 발견하는 일을 막기 위한 것이다.
  • 기존에 BDD 기반 테스트 자동화(Cucumber 활용)를 수행해 왔으며, 본 시스템의 시나리오 계층도 같은 방식을 따른다.

2. 왜 일반적인 방법으로는 안 되는가 — 3가지 전제

본 사업을 이해하는 데 필요한 전제는 아래 3가지가 전부다.

전제 1 — UI 객체를 인식할 수 없다

메뉴·버튼이 네이티브 UI 요소로 존재하지 않는다. 화면 대부분이 단일 웹뷰이거나, 클라우드 스트리밍 서버가 방송 화면 위에 UI를 그려 하나의 영상으로 내려보내는 방식이다. 즉 셋톱이 보여주는 것은 사실상 "그려진 그림"이며, uiautomator 계층은 비어 있다(부속서 C1).

→ 셀렉터 기반 자동화 불가. 화면을 이미지로 판독하는 수단이 필수.

전제 2 — 화면 확보 경로는 2가지다

대상 확보 방법 용도
정지 화면(스틸컷) 셋톱에 ADB 명령으로 UI 스크린샷 취득 메뉴·설정·목록 등 정적 화면 판정
움직이는 화면(영상) 셋톱 HDMI 출력 → 캡처보드 → PC 재생 여부·전환 효과·순간 노출(토스트) 등 동적 판정

주의할 실측 사실: 방송·재생 영역은 ADB 캡처 시 검정으로 찍힌다(부속서 C2). 따라서 영상 관련 판정은 캡처보드 경로가 유일하며, 캡처보드 사용 가능 여부(HDCP)는 착수 초기에 실측으로 확인해야 한다(부속서 C20, 4.3).

전제 3 — 실시간 판독 방식과 AI 모델은 미확정이다

실시간 영상을 어떤 파이프라인으로 처리할지, 판독에 어떤 모델을 쓸지는 아직 확정하지 않았다. 개발사의 제안 항목이다(→ 8장).

4. 핵심 판정 정책 — 기능 판정과 디자인 판정의 분리

본 시스템에서 가장 중요한 개념이다. 화면에서 AI가 추출한 정보를 "기능 요소"와 "디자인 요소"로 나눠 각각 다르게 판정한다.

판정 결과 조건 처리
PASS 기능 정상 + UI가 기준과 일치 통과
PASS (변경 감지) 기능 정상 + 디자인만 변경 통과로 집계하되, 변경점을 리포트에 하이라이트하고 알림 발송
FAIL 기능이 동작하지 않거나 기능의 방향성이 다름 제품 결함
ERROR 전제 미충족·장비/판독 문제로 판정 불가 FAIL과 분리 집계 (제품 결함이 아님)

예시 — 음량 게이지

음량을 올리고 내리면 화면 우측에 게이지가 표시된다. 최근 업데이트로 게이지 형태가 바뀌었다고 하자.

구분 기존 UI 변경된 UI
게이지 형태 점 32개로 구성 선(bar) 형태로 변경
음량 단계 0~32, 하단 숫자 표시 0~32, 동일

이때 판정은 다음처럼 갈린다.

검사 항목 분류 판정
음량+ 입력 시 게이지가 표시되는가 기능 정상 → 문제없음
음량+ 시 수치가 증가하는가 / 음량− 시 감소하는가 기능 정상 → 문제없음
음량 범위가 0~32로 유지되는가 기능 정상 → 문제없음
게이지가 점이 아니라 선으로 바뀌었다 디자인 기능과 무관한 변경

→ 최종 결과: PASS (변경 감지) — 테스트는 통과 처리하고, "게이지 형태가 점→선으로 변경됨"을 리포트와 알림으로 통지한다.

반대로, 음량+를 눌렀는데 게이지가 아예 표시되지 않거나 수치가 감소한다면 디자인과 무관하게 FAIL이다.

구현 관점: 이 정책은 "AI에게 합격 여부를 묻는 것"이 아니다. AI는 화면에서 {게이지 존재, 형태 특징, 현재 수치, 최대 단계} 같은 구조화 데이터를 추출할 뿐이고, 어떤 필드가 기능 요소이고 어떤 필드가 디자인 요소인지, 어느 쪽 불일치를 어떻게 처리할지는 화면별 판정 스키마(코드) 가 정의한다. 3장의 설계 원칙과 충돌하지 않는다.

5. 문서 리포지토리와 기준(Baseline) 자동 반영

UI 변경이 계획된 것인지를 시스템이 스스로 알게 하는 기능이다. 이를 위해 기획·설계 문서를 모아 두는 문서 리포지토리를 두고, AI가 문서를 판독해 판정 기준(Baseline)을 갱신한다.

5.1 문서 리포지토리

항목 내용
대상 문서 기획서(화면·기능 변경 명세), 설계서(동작 규칙·상태 정의), UI 디자인 가이드(색·폰트·컴포넌트 규격), 원 TC 목록
저장소 형태 Git 저장소 권장 — 버전·이력·diff가 그대로 확보된다. 고객 환경에 따라 Confluence·SharePoint·공유 폴더 + 변경 감시로 대체 가능 (착수 시 협의)
구조 예시 /docs/기획서/{화면명}/ · /docs/디자인가이드/ · /docs/설계서/ · /baseline/{화면명}/{버전}/
운영 규칙 파일명에 대상 화면·버전을 표기하고 업로드 권한·검수자를 지정한다. 리포지토리 반입이 곧 "계획된 변경"의 등록 행위가 된다

문서 유형 추출 대상 기준에서의 역할
기획서 변경 화면·요소·기대 동작·적용 시점 "계획된 변경"의 등록 — 5.3 판정 분기의 근거
UI 디자인 가이드 색·폰트·형태·간격 등 디자인 요소의 허용 규격 기능 요소/디자인 요소 구분(4장)의 기준선 — 무엇이 "변해도 되는 것"인지를 문서로 정의
설계서 동작 규칙(상태 전이·조건) 기능 판정 규칙 보강
  • 추출 결과는 자동 반영 전 사람 검수(승인) 단계를 거친다 — 잘못 판독된 기준이 판정 전체를 오염시키는 것을 막는다.
  • 기준은 버전 관리되며, 과거 기준으로의 재판정이 가능해야 한다(부속서 FR-38).

5.3 판정 분기

상황 판정
리포지토리에 등록된 변경이 화면에서 확인됨 PASS — "계획된 변경 반영 확인"으로 표시 (불필요한 알림 없음)
리포지토리에 없는 변경이 감지됨 PASS(변경 감지) — "미등록 변경" 알림 발송
변경이 등록됐는데 화면은 이전 UI 그대로임 알림 — "기획 미반영" 통지
  • 지원 문서 포맷(PDF·PPT·이미지·위키 등)과 저장소 연동 방식은 개발사 제안 항목(→ 10장).

6. 시나리오 작성 방식 — BDD

테스트 시나리오는 BDD(Gherkin) 형식의 텍스트 코드로 관리한다(버전 관리·diff·검색 가능 — 부속서 P8). 당사는 Cucumber 기반 자동화 수행 경험이 있어, 시나리오 표현 방식은 아래 형태를 기준으로 협의한다.

기능: 음량 조절 UI

  시나리오: 리모컨으로 음량을 올린다
    조건   실시간 방송을 시청 중이다
    만일   리모컨 [음량+] 키를 누르면
    그러면 화면 우측에 음량 게이지가 표시된다
    그리고 음량 수치가 1 증가한다
    그리고 게이지 UI가 기준과 다르면 "변경 감지"로 기록한다
  • 시나리오의 각 step은 화면 단위 객체(진입·앵커·조작을 한 곳에 모은 코드 단위)를 호출한다. 화면이 바뀌면 그 화면 단위 1곳만 고치면 되도록 한다(부속서 P7·FR-14~15).
  • 원 TC(QA가 작성한 자연어 명세)에서 시나리오 코드 초안을 AI로 생성하는 파이프라인도 과업에 포함된다(부속서 WBS-9, FR-43~45).

상세·전체 목록은 부속서 5장(FR-1~67). 아래는 개발사가 규모를 가늠하기 위한 요약이다.

그룹 요구사항 요약 부속서 연결
A. 디바이스 제어 ADB 네트워크 연결, 리모컨 키 추상화(연속 키 500ms 이내 제어), 스크린샷·버스트 캡처, 시스템 상태 조회 FR-1~6
B. 화면 판독 한국어 OCR(신뢰도·좌표 포함), 판독 결과 재사용(중복 인식 방지), 비전 모델의 스키마 강제 구조화 출력, 벤더 2종 이상 전환 가능 FR-7~13, 19~30
C. 판정 기능/디자인 분리 판정(4장), 4분류 결과, 기준 대비 변경점 산출, 목록 순서·말줄임·상대 시각 판정 FR-64~66, P6

F. 시나리오·실행 BDD 실행, 선택 실행, TC 단위 타임아웃·teardown, 한 건 실패가 전체를 멈추지 않음 FR-31~32
G. 리포트·알림 셀프컨테인드 HTML 리포트(외부 리소스 없이 열림), 변경점 하이라이트, ERROR 시각 구분, 변경 감지 알림 발송(채널은 협의: 메일·메신저 등) FR-33~37
H. 제작 파이프라인 원 TC → 시나리오 코드 초안 생성, step 커버리지 대조, FAIL 원인 1차 분류(트리아지) FR-43~50

8. 모델·도구 권장안 — 운용 경로 2가지

본 시스템은 운영 환경의 네트워크 정책에 따라 두 가지 경로로 구축·운용할 수 있어야 한다.

운용 경로 환경 판독 모델
경로 ① 온라인 외부(또는 사내 계약 클라우드) 접속 가능 클라우드 프론티어 모델 API (Claude·Gemini 등)
경로 ② 오프라인 차단망 — 외부 접속 불가 자체 GPU 서버의 로컬 오픈 모델 (Qwen3-VL 등)

핵심 설계 요구: 두 경로에서 판정 코드는 동일해야 하며, 모델 엔드포인트만 설정으로 전환된다. 경로 선택이 코드 재작성으로 이어지는 설계는 받지 않는다. (부속서 근거 제안서 §1.3의 모델 경로 A/B가 경로 ①, C/D가 경로 ②에 해당)

8.6 권장 전략 — 단계적 결정

  1. POC(11장)는 경로 ①로 시작한다. 초기 비용 0으로 첫 주부터 가능하고, 골든 세트·스키마·판정 구조를 프론티어 정확도에서 먼저 검증하는 것이 순서다. 이때 만든 골든 세트가 그대로 경로 ② 모델의 채용 시험지가 된다.
  2. 보안 검토 결과가 운영 경로를 정한다. 전송이 승인되면 경로 ①(프라이빗 엔드포인트)을 운영 기본으로 하고 경로 ②의 소형 모델을 폴백으로 둔다. 승인되지 않으면 경로 ②로 전면 전환한다 — 판정 구조가 같으므로 코드 재작성이 없어야 한다(8.1).
  3. 절충안 — 판정과 제작의 분리. TC 코드 초안 생성(제작 파이프라인)은 원 TC 텍스트와 코드만 다루고 화면을 전송하지 않는다. 따라서 판정은 차단망(경로 ②)에서 하되, 제작만 별도의 인터넷 가능 개발 환경에서 경로 ①로 수행하는 구성이 가능하다. 보안 정책상 허용 여부를 확인할 가치가 있다.
  4. 계약·문서에는 모델명을 고정하지 않는다. 모델 세대가 분기마다 바뀌므로 "스냅샷 버전 고정 가능(경로 ②는 해시 고정) + 골든 세트 필드별 정확도 ≥ 0.98 통과"를 조건으로 걸고, 구체 모델명은 착수 시점의 Phase 0 실측 비교로 확정한다. 본 장의 모델명은 그 비교의 출발 라인업이다.

9.2 JIRA 자동 연계 (고객사 JIRA)

FAIL 건은 사람이 옮겨 적지 않는다 — 러너가 JIRA REST API로 이슈를 자동 생성한다.

항목 내용
이슈 생성 대상 FAIL(제품 결함)만. ERROR(판정 불가)는 이슈를 만들지 않고 별도 집계한다 — 결함이 아닌 것으로 결함 큐를 오염시키지 않는다
이슈에 담는 것 TC id·실패 step, 판정 시점 스크린샷/클립, 인식 덤프, FAIL 트리아지 결과(5분류 태그 + 원인 서술 + 재현 조건), 회차 리포트 링크
중복 방지 동일 TC의 미해결 이슈가 있으면 새 이슈 대신 코멘트로 재발을 기록한다 — 같은 결함으로 이슈가 쌓이지 않게
변경 감지의 처리 PASS(변경 감지)의 "미등록 변경"은 결함이 아니므로 기본은 대시보드·알림으로만 노출. 옵션으로 확인용 태스크 생성 가능 (협의)
매핑 JIRA 프로젝트·이슈 타입·필드·라벨 매핑은 착수 시 고객사와 협의 (→ 10장)

9.3 대시보드 (접속 URL)

회차 리포트(셀프컨테인드 HTML)는 실행 1회의 산출물이고, 대시보드는 URL로 접속하는 상시 웹 서비스다. 결과 DB 위에서 다음을 보여준다.

화면 내용
실행 추이 회차별 PASS / PASS(변경 감지) / FAIL / ERROR 추이, 실행 시간
최신 결과 최근 스위트의 TC별 결과, FAIL 상세(스크린샷·JIRA 이슈 링크)
변경 감지 현황 미등록 변경 목록, 등록(계획된) 변경의 반영 확인 현황
TC 히스토리 TC별 이력 — 불안정(플레이키) TC 식별
  • 사내망 웹 서비스로 배포하며 호스팅 위치·접근 인증은 협의한다. 회차 리포트는 대시보드에서 링크로 열람한다.

10. 미확정 사항 — 개발사 제안 요청

아래는 발주 측이 의도적으로 확정하지 않은 항목이다. 제안서에 반드시 대응 방안을 포함해 달라.

# 항목 현황 제안 요청 내용
1 운용 경로 확정 (①/②/병행) 보안 검토 결과 대기 경로 ①·② 양쪽의 수행 방안과 견적을 각각 제출 (경로 ②는 GPU·서버 사양 포함). 8.1의 "같은 코드, 설정 전환" 충족 방안 명시
2 AI 모델 확정 8장에 권장 라인업 제시 8.6-4의 조건(스냅샷/해시 고정 + 골든 세트 ≥ 0.98)으로 Phase 0 비교 후 확정. 벤더·모델 2종 이상의 한국어 셋톱 UI 샘플 추출 정확도 실측 근거 제출 (당사가 샘플 제공)
3 실시간 영상 판독 처리 방식 미확정 캡처보드 프레임 스트림의 처리 파이프라인(프레임 샘플링·클립 추출·동기화 등) 설계안
4 HDMI 캡처 가능 여부 HDCP 적용 여부 미확인 착수 초기 실측·보고 절차. 캡처 불가 시 영상 판정 과업은 미착수·감액 (부속서 4.3의 게이트 구조 준수)
5 문서 리포지토리 포맷·연동 협의 필요 지원 문서 포맷(PDF·PPT·이미지·위키 등)과 저장소(Git 등) 연동 방식
6 JIRA·CI/CD·대시보드 연동 사양 고객사 환경 확인 필요 JIRA 프로젝트·이슈 타입·필드 매핑, CI 도구(Jenkins·GitLab CI 등), 대시보드 호스팅 위치·접근 인증 방식 제안

제안 평가에서 탈락하는 답 (부속서 11장): 검정으로 찍히는 재생 화면을 "캡처해서 보겠다"는 답, 실시간 방송 판정을 캡처보드 없이 풀겠다는 답, HDCP를 확인 없이 "문제없다"고 전제한 답, 모델에게 PASS/FAIL을 직접 묻는 설계, 경로 전환 시 코드 재작성이 필요한 설계.

11. 우선 추진 범위 — POC 2건

전체 구축에 앞서 아래 2건의 POC를 먼저 수행한다. 목적은 ① 정적(ADB 스크린샷)·동적(캡처보드) 두 판정 경로의 실증, ② AI 판독 정확도와 4장 판정 정책(변경 감지 포함)의 검증이다. 대상 원 TC(테스트케이스)는 현재 확보 진행 중이며 착수 시 제공한다.

구분 POC 1 — Btv Wing UI POC 2 — VOD Player
대상 실시간 방송 시청 중 리모컨 키로 여는 윙 UI (편성표·장르별 메뉴·설정 패널·시청 예약 등) VOD 재생·일시정지·구간 이동 등 플레이어 조작과 재생 화면 상태

사전 확인된 사실 부속서 부록 C에 원 TC 55건 표본 분석 완료: 42건(76%) 전건 자동화 가능, 필요 화면 객체 8종 재생 여부는 오디오 트랙 상태로 판정 가능함을 실측 확인(부속서 C4). 재생 영역은 ADB 캡처 시 검정으로 찍히므로(C2) 화면 상태 판정 일부는 캡처보드(트랙 B) 필요 — HDCP 확인과 연동

12. 개발 범위와 단계 (안)

세부 WBS는 부속서 4장. 단계 구성은 개발사 제안으로 조정 가능하며, Phase 1은 11장의 POC 2건을 기점으로 한다.

단계 내용 비고
Phase 1 — 기반 디바이스 제어 + 스틸컷(ADB) 판독 + 판정 엔진 + BDD 러너 + 리포트 정적 화면 TC부터 자동화 개시
Phase 2 — 영상 HDCP 실측 → (가능 시) 캡처보드 연동 + 실시간 영상 판정 조건부. 별도 견적 항목으로 분리
Phase 3 — 지능화·연계 문서 리포지토리 자동 반영(기준 갱신) + 변경 감지 고도화 + 원 TC → 코드 초안 생성 + FAIL 트리아지 + JIRA·CI/CD·대시보드 연계

발주 측 제공 사항(셋톱 실기 최소 2대, 테스트 계정, 원 TC 목록, 캡처보드, 모델 API 계정, 실측 자료)은 부속서 7장을 따른다.

13. 검수 기준 (핵심만)

수치·건수를 포함한 전체 기준은 부속서 8장(AC-1~32). 개발사가 방향을 잡기 위한 핵심은 다음과 같다.

무엇을 확인하나 합격의 의미
지정 원 TC의 자동 실행·판정 전건 실행 완료, 기대 결과 일치
재현성 동일 TC 연속 10회 실행에서 PASS/FAIL이 갈리지 않음 (판정 불가는 ERROR로 분리)
기기 이식성 동일 코드가 셋톱 2대에서 동작, 기기 차이로 인한 FAIL 0건
변경 감지 판정 디자인만 변경된 화면 시나리오에서 FAIL이 아니라 PASS(변경 감지) 로 분류되고 알림이 발송됨
기획서 반영 업로드된 기획서의 변경이 기준에 반영되고, 등록/미등록 변경이 구분 표시됨
근거 보존 임의 FAIL 건에서 판정 시점 화면·인식 덤프·모델 응답이 아티팩트로 확인됨
리포트 네트워크 차단 상태에서 열람 가능, ERROR가 시각적으로 구분됨
경로 전환 설정 변경만으로 판독 모델을 경로 ① ↔︎ ②로 전환했을 때 코드 수정 0줄, 결정론 판정 결과 동일
오프라인 설치·실행 (경로 ② 채택 시) 외부망을 차단한 환경에서 문서만 보고 설치가 완료되고, 로컬 모델만으로 전체 스위트가 완주됨
JIRA 자동 이슈 FAIL 시나리오에서 이슈가 자동 생성되고(아티팩트·리포트 링크 포함), 동일 TC의 반복 FAIL은 중복 생성 없이 코멘트로 갱신됨. ERROR는 이슈 미생성
대시보드 접속 URL에서 실행 추이·최신 결과·변경 감지 현황이 열람됨
